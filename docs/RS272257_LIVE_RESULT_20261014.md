## 已定位的系统问题

1. API 请求稳定性：一次 Planner 请求成功，其余多个请求失败。BM 第二轮有明确 APIConnectionError 证据；其他失败只有 ModelProviderError 分类，不能一概宣称相同根因。保留各目录 failure.json/model_calls.jsonl。
2. TB 工具兼容性：对 RiBM 原始模型 TB 使用无网络 Docker 编译，Icarus 报 `break statements not supported`，定位第58行。证据在 `runs/rs_ribm_live_20261014_01/tb_compile_check.json`。编译时使用受控回放桩提供 DUT 声明，回放桩不是生成的 RS 实现。已给后续 TB 生成提示加入 Icarus 限制，原始失败 TB 不变；尚未验证提示修改后的真实模型输出。
3. 用量记录：已给 TB 角色接入 RecordingProvider。首轮 TB 请求不在统计内，失败请求也未上报 token；不得把未知数记为0。RiBM 成功 Planner 返回926输入/2254输出 token，只是可见部分。
4. 采样可复现性：成功 Planner 请求记录的 temperature/top_p 为0.1/1.0，服务响应元数据为1.0/0.98；保留差异，不能据此确定服务实际采样实现。请求与响应均标记模型 gpt-5.6-terra。
5. 实验入口：增加 TB 复用来源/hash 和可选请求超时，指定超时时关闭 SDK 自动重试，避免重复请求次数不清楚。

后续先恢复同一服务的稳定调用，再生成并验证 KES RTL；之后才扩展完整译码器和 Vivado。未更换用户指定模型或服务，未将人工 RTL冒充模型结果。

## 后续流式及 Vivado 试验

- 新增可选 Responses SSE 流式。必须收到 `response.completed` 才接收 JSON，断流丢弃片段；单元测试覆盖完整流和缺少终结事件。
- 调整实验入口为先生成 RTL、通过固定检查器，再生成模型 TB；`--stage rtl` 可单独测 RTL。BM 的流式 Planner 成功（147936ms），但 Generator 在约 62707ms 时失败。任务数据库最后事件的原文为 `provider request failed: RemoteProtocolError: peer closed connection without sending complete message body (incomplete chunked read)`。因此流式没有解决本次中转连接中断；不得把此类失败归因于 RTL 算法。
- 找到本地 Vivado 2026.1，可用 BASIC 许可证和 289 个器件。`xc7a12ticsg325-1L` 上的小型 8 位测试模块完成 OOC 综合并输出报告（6 LUT、8 寄存器）；这是工具链冒烟验证，非 RS 设计。
- 首次 Vivado 冒烟在综合后才创建时钟，报告 WNS 为 `inf`，不构成有效时序验收。Tcl 已改成综合前读取时钟 XDC，并把冒烟模块改成有寄存器到寄存器路径。复测在 10 ns 时钟约束下得到 7 LUT、16 个寄存器、WNS 8.884 ns；`runs/vivado_smoke_20261014_reg2reg/{utilization,timing}.rpt` 是原始证据。Vivado 报 OOC 时钟源 `HD.CLK_SRC` 未设置，所以这里仅证明综合与基本时序报告链路可用，不代表布局布线后时序、功耗或 RS 设计表现。
- 本地单元测试 24 通过、2 个 Docker 测试默认跳过；提权运行该 Docker 集成测试后 2 项通过，确认固定黄金 TB 可接受受控回放桩并拒绝错误输出/未完成设计。回放桩只检验检查器，不是 RS RTL。

## 可复现入口

保持项目当前 `.env` 中的用户指定服务与模型，不在命令中写 API 密钥：

```powershell
.venv\Scripts\python.exe -m verilog_agent.benchmarks.rs_demo --algorithm bm --root runs/rs_bm_next --live --stage rtl --stream --request-timeout 180
.venv\Scripts\python.exe -m verilog_agent.benchmarks.rs_demo --algorithm ribm --root runs/rs_ribm_next --live --stage rtl --stream --request-timeout 180
```

每次使用新目录，保留失败证据。只有 `run_result.json` 显示固定黄金 TB 验证通过，并确认 `selected_candidate_id` 有对应 RTL 文件后，才用 `rs_synth.tcl` 调 Vivado；不能把请求重试成功等同于 RTL 功能成功。示例（将 `$rtl` 替换成真实候选文件的绝对路径）：

```powershell
& 'D:\AMDDesignTools\2026.1\Vivado\bin\vivado.bat' -mode batch -source 'D:\AI\VerilogMulti\VerilogAgent\verilog_agent\benchmarks\rs_synth.tcl' -nolog -nojournal -tclargs $rtl rs_kes_bm xc7a12ticsg325-1L 'D:\AI\VerilogMulti\VerilogAgent\runs\rs_bm_synth' 10
```

`--stage all` 才继续生成 Agent TB；其检查不能替代独立固定黄金 TB。目前 BM/RiBM 均没有经验证 RTL，故没有可提交的 RS 综合数据。
